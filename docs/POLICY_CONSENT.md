# Marketplace policy consent — disabled infrastructure

[GBXMRKT-26](https://linear.app/mxndev/issue/GBXMRKT-26) requires explicit signup acceptance of founder-approved Terms and Privacy versions. As of November 11, 2026, [GBXMRKT-2](https://linear.app/mxndev/issue/GBXMRKT-2) has no approved operator legal name/address, effective wording, immutable version URLs or effective dates. `/terms` and `/privacy` contain development-only review drafts and return 404 outside development. These drafts must never become acceptance evidence.

## What is implemented

`convex/lib/policyConsent.ts` deliberately sets `PUBLISHED_POLICY_PAIR` to `null`. `users.publishedPolicies` returns `null`; `users.acceptPolicies` rejects all attempts without creating records. There is no environment switch to activate draft consent. Email and Google **signup** now hand off through `/accept-policies`, which preserves a validated local return path. While no policies are published, that page continues without recording acceptance. The former signup checkbox against draft policy links was removed. Existing users sign in normally without a new acceptance record, as the founder directed on November 15. Protected marketplace actions still do not distinguish new accounts from exempt legacy accounts, so this preparation does not satisfy the launch gate today.

For a future reviewed release, the acceptance mutation requires authenticated, provisioned, nonsuspended identity, explicit acceptance, and an exact match with the server's published version pair. It uses server time and server-owned version links/effective dates. Each user/version pair has one immutable evidence row, looked up and inserted in the same Convex transaction. Retries return the original record ID and timestamp; a later pair creates a separate row. Convex transaction conflict retries provide concurrent-write protection; real simultaneous-client behavior still needs staging verification.

Evidence is stored in the separate `policyAcceptances` table with Convex user ID, Clerk user ID, terms/privacy versions, exact policy URLs/effective dates, and server acceptance timestamp. No evidence fields are added to `users`, public seller projections or listing responses. `users.policyAcceptanceHistory` reads only the authenticated owner's history. `users.inspectPolicyAcceptanceHistory` requires an active admin or super-admin and a support reason, returns at most 50 rows per page, and atomically writes `policy_acceptance_read` to `adminAuditLog`. Other support staff receive no implicit access.

`users.currentPolicyStatus` gives the signed-in account its current published pair, provisioning state, and whether that exact pair has an acceptance record. When a pair is live, signup displays a notice next to both the email and Google actions: clicking either accepts the linked exact versions. A short-lived, same-tab intent carries that button action through Clerk verification or redirect; it is not itself policy evidence. After provisioning, the consent handoff records acceptance through the server mutation only if the intent still matches the current pair. Missing, stale, or unavailable intent falls back to an unchecked acceptance form for that signup attempt. Existing sign-ins continue without being inferred to have consented. A stale pair is rejected by the server and must be reviewed again. A client redirect alone does not prevent direct marketplace mutations, so server action checks for new accounts are still required before publication.

## Provisioning and legacy treatment

Clerk's signed webhook provisions the Convex user independently. It never copies checkbox or unsafe-metadata values into consent evidence. A Clerk account can therefore exist before its Convex user or any acceptance record. Acceptance before provisioning fails without side effects; after provisioning the same explicit action can retry. An unsigned request, missing JWT, unknown account or suspended account cannot record acceptance.

Existing users remain without acceptance evidence and may continue using the marketplace without a new acceptance step, per the founder's November 15 decision. Do not backfill acceptance timestamps or infer acceptance from account creation, sign-in, a prior checkbox, or policy publication. New accounts created after publication still need an acceptance record before protected marketplace actions; define the reliable account cutoff and direct-action enforcement before activation. Records remain separate from user rows and are not cascaded away by the existing Clerk deletion callback. Account deletion and consent retention need the approved privacy/operational decision below before activation.

## Activation work and decisions still required

1. Founder approves final policy wording, operator identity, immutable versions/URLs, effective dates, and consent retention. Preserve the content at each accepted URL indefinitely for the approved evidence lifetime; do not reuse a version for changed text.
2. Complete the account-provisioning flow and protected-action boundary. The prepared flow allows an authenticated Clerk/Convex account pending consent. New signup actions display a linked policy notice and can record the exact version pair after provisioning; the manual form remains for missing or changed intent. Existing accounts are exempt and must be distinguished reliably from new accounts without inventing acceptance evidence. Direct API calls by new accounts are not gated. Decide which new marketplace actions require current acceptance and which existing obligations, safety and support actions remain available. A route-only gate is insufficient.
3. Preserve the intended return path and form progress. On version mismatch, reload the current pair, clear the acceptance control, and require a new explicit action. Retry transient provisioning/network failures without substituting a newer pair or creating contradictory evidence.
4. Document the legacy-account exemption and reliable new-account cutoff. Future material-update re-consent is a separate founder decision: adding a new published version must never silently rewrite old evidence or automatically impose an unapproved update rule.
5. Complete new-account direct-route and protected-action checks, approved immutable policy routes, and the server registry in one reviewed activation change. An absent registry must fail closed for new signup and protected actions, while exempt legacy accounts retain access. The prepared handoff and disabled primitive alone are not a launch-ready signup gate.
6. Publish the approved privacy retention statement. Working wording for review: “We keep the policy versions you explicitly accepted, your account identifiers and the acceptance time as evidence of that acceptance. Authorized staff access is restricted and recorded.” Add the founder-approved duration, deletion treatment and purpose before publication; no duration or legal basis has been invented here. There is no consent purge scheduled and no effective-policy records can currently be created.

## Verification before release

Run `pnpm --filter @gearboxe/web exec node --experimental-strip-types --test scripts/policy-consent.test.mjs`, web lint and typecheck. Synthetic policy fixtures test the record primitive only; they do not publish or approve policies. Tests cover disabled/missing consent, stale versions, future effective dates, authenticated identity/server timestamps, retry idempotency, version history, provisioning lag, duplicate Clerk callbacks, legacy users, public projection privacy and audited administrator reads.

After the activation change and hosted environment recovery, use isolated staging with real Clerk/Convex. Test desktop/mobile email and Google signup button intent, policy links without losing progress, missing/stale intent fallback, legacy-account exemption without false records, missing consent and direct protected requests by a new account, a policy change during signup, callback/network retry, and simultaneous acceptance calls. Verify exactly one original timestamp per pair through the owner's history; repeat as another ordinary account and confirm denial. An administrator should use `users.inspectPolicyAcceptanceHistory` with the test account's Convex ID, a case reason and pagination options, then verify its audit event. Record deployment IDs, approved versions, UTC time and redacted outcomes. Do not use production accounts or public test listings. GBXMRKT-26 remains incomplete until these gates pass.
